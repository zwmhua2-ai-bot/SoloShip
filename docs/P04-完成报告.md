## A. 状态索引

目标：**不指定任务 ID，也能正确定位到 `p03d_remove_002`。**

关键设计：

- `scope=development`：索引区分「开发任务」与「交接记录」，3 条更晚的 P00 交接记录不会顶掉更早的开发任务。

## B. 集成指令（WORK-INSTRUCTIONS.md）

面向 ChatGPT Work 的操作规则，核心约束：

1. 只读消费 `exchange/status/*`，不直接读数据库。
2. 状态必须带 `state_basis`，区分历史执行结论与 GitHub 实时状态。
3. 不得把「测试名存在」当作「验收通过」。
4. 状态不确定时明确写「不可确认」，不用推断填补。

配套自检项 7–9：检查索引新鲜度、检查 `verified=False` 是否被误读、检查 PR 编号是否为数字。

## C. AI 验收助手

初版缺陷：只要验收项关键词在测试名里出现，就标 `covered_by_test_names` —— 这是**过度断言**。

改为三态判定，且恒 `verified=False`：

| 判定 | 含义 |
| --- | --- |
| `assertion_seen_in_diff` | 在 diff 新增行里找到对应断言 |
| `partially_covered` | 只覆盖了部分关键词 |
| `test_name_only` | 只有名字相近的用例，无断言证据 |
| `unverified` | 无任何证据 |

每条结果都带 `missing_tokens`、`possible_tests`、`uncertainty`，并统一输出 `verdict=needs_human_review`。

### AC-04 的真实结论（保留不确定性）

- 状态：`partially_covered`
- 缺口 token：`["list_all"]`
- 可能相关的用例：`["test_add_and_list", ...]`
- `verified = False`，需人工复核

> 这一条是 P04 的核心价值：**验收助手不替人下结论，只把「差在哪」说清楚。**
