# SoloShip v0.2 方向与需求讨论备忘录

> **文档状态：讨论稿 / 待 v0.1 完成后重新评审，不构成开发授权**  
> 记录日期：2026-10-24  
> 建议入库路径：`docs/V02_ROADMAP_DRAFT.md`  
> 信息来源：用户与 ChatGPT 已有的 SoloShip v0.2 讨论；下列架构与竞品判断是**讨论所得的初步方向**，并非已经批准的需求、已实现的功能或已验证的基准测试。

## 0. 一页摘要

**产品愿景**：用户提供一个现有项目仓库（或新项目目标）及要求，SoloShip 自动理解代码与目标、制定 Roadmap、拆分依赖明确的任务、调用编码 AI 逐项实现、运行可信测试、进行独立审查与受限修复，最终交付可运行、可审查的整体项目；用户主要负责关键授权与最终验收。

我们讨论后形成的**优先级共识**：

1. **先完成 v0.1**。不因 v0.2 设想扩大当前任务范围。
2. **v0.2 优先完成“整项目规划 → 自动拆卡 → 串行连续执行 → 项目级验收”**，核心价值是减少用户逐张派卡的次数，而不仅是提高执行速度。
3. **复用 v0.1 的 Bridge、Codex 执行、Validator、Reviewer、Journal、Draft PR 和确定性门禁**，不推倒重做，也不先堆叠大量 Agent。
4. **双 Worker / 多项目并发是讨论过的候选能力，暂不作为 v0.2 首要交付目标**；是否安排在 v0.2 后段或 v0.3，待 v0.1 验收与 v0.2 工作量评估后决定。
5. **规划权不等于授权权**。AI 可以提出任务和技术方案，但不得自动扩大文件、仓库、测试命令、网络、凭据、支出、发布、合并或部署权限。所有真实副作用仍受确定性 Bridge 控制。

## 1. 用户真正希望得到的体验

### 1.1 典型输入

- 一个已有 Git 仓库或明确的新项目目标。
- 产品目标、业务功能、技术栈或约束、验收方式。
- 项目范围与风险边界（授权仓库、允许操作、预算/时间/任务数上限等）。

例子：

> “这是一个 Python + React 项目。我希望它成为个人财务管理系统，支持登录、收支记录、统计图表和数据导出。请分析现状，提出计划；计划获批后，你自行拆解和完成开发，只有关键决策与最终结果再找我。”

### 1.2 预期输出

- **可审查的项目计划**：当前代码与目标差距、架构选择、里程碑、依赖、风险、验收标准。
- **可执行的任务图**：任务 ID、依赖、实现范围、测试方案、证据要求。
- **持续的开发结果**：每项任务的代码提交、检查结果、Reviewer 结论、修复历史、失败/暂停原因。
- **项目级交付**：跨模块集成检查、未解决事项、Draft PR 或等效交付入口、人工验收说明。

**边界**：不承诺任意复杂项目都能一次自动完成；遇到需求重大歧义、关键证据不足或高风险操作，应暂停并请求人工决策。

## 2. 版本定位与当前约束

| 版本 | 核心目标 | 讨论状态 |
|---|---|---|
| v0.1（当前） | **一张任务卡**可靠自动完成：校验 → 实现 → 测试 → 审查/修复 → 证据 → Draft PR / 人工验收 | 继续收尾，不改范围 |
| v0.2（优先方向） | **一个项目目标**自动规划多张任务卡，按依赖**串行执行**，最后做项目级验收 | 本文仅记录方向，待批准 |
| v0.2 可选扩展 | 双 Worker、不同项目并行、成本与限流感知 | 讨论过，但优先级低于项目自动编排 |
| 更后续版本 | 动态 Worker 池、多后端/多模型深度路由、桌面看板、复杂资源调度 | 不在当前承诺中 |

v0.1 目前是**全局单任务执行**，可以管理多个项目和任务，但同一时间自动执行一张任务卡。这不妨碍 v0.2 先实现整项目的**串行**自动开发。

## 3. v0.2 候选核心工作流

```text
用户提供项目仓库 / 新项目目标 + 约束
            ↓
[项目分析] 静态识别代码、依赖、测试、缺口、风险
            ↓
[项目规划] 目标 / Roadmap / 里程碑 / 验收定义
            ↓
[计划校验] 范围、依赖、预算、权限、可测试性
            ↓
[人工批准规划与授权边界]  ← 需要时澄清关键歧义
            ↓
[任务图 Task Graph] 生成依赖明确、可校验的任务卡
            ↓
[Bridge 串行调度] 选择依赖已满足且已授权的任务
            ↓
[现有 v0.1 流水线] Builder → 真实测试 → Reviewer
                              ↑              ↓
                              └─ 有上限修复 ──┘
            ↓
[任务证据门禁] 通过 → 解锁依赖任务；失败 → 阻断并留证据
            ↓
[项目集成验收] 跨任务、跨模块、业务 AC 与端到端检查
            ↓
[最终报告 / Draft PR] → 用户体验、确认与人工合并
```

**设计原则**：先全局粗规划，再按阶段细化，不要求初次规划一次性把全部实现细节预测准确。计划修订必须保留版本与审批记录。

## 4. 关键能力模块（候选）

### 4.1 Project Analyzer（项目分析阶段）

- 静态读取允许访问的仓库文件、项目结构、依赖、现有测试、README 与工程规范。
- 输出“已实现 / 待开发 / 不确定”的差距清单及需要人工确认的问题。
- **分析默认只读**；不得为了识别项目而自动运行不可信脚本。

### 4.2 Project Planner（项目规划阶段）

- 从目标与差距产生 Spec、Roadmap、阶段计划、任务列表和可验证的 AC。
- 每项任务注明修改范围、前置依赖、测试方案、风险及是否需审批。
- 复杂任务先评审计划，简单任务可采用轻量流程，避免过度消耗模型资源。
- Analyzer / Planner / Plan Validator 是**逻辑职责**，不代表一开始就要增加三个常驻 Agent；优先复用现有角色与确定性校验器。

### 4.3 Task Graph（任务图与调度）

- 管理任务 ID、依赖、优先级、版本、阻断原因、审批状态与证据引用。
- 拒绝循环依赖、缺失依赖、越权的生成任务与无限新增任务。
- 初版仍**单 Worker**：一次只执行一个依赖满足的任务；失败不能自动解锁其依赖任务。
- 所有执行继续走已有 Bridge 门禁；Planner 不得通过任务 JSON 扩大授权。

### 4.4 连续执行与恢复

- 重用 v0.1 的 P02 开发、真实测试、独立 Reviewer、修复上限和证据持久化。
- 任务级恢复与项目级进度对账必须一致；不能因重启重复调用 Codex、重复提交或重复创建 PR。
- 对预算耗尽、反复失败、权限不符、证据冲突、人工审批未获批等情况明确暂停。
- 与 v0.1 的 P05-C 完成情况和实际安全边界对齐，不绕过其恢复门禁。

### 4.5 项目级验收（不是所有单项测试通过就算完成）

- 每条业务 AC 映射到明确证据：测试名称/结果、候选 SHA、Reviewer 结论、必要的人工检查。
- 识别单项任务通过但跨模块集成失败的情况。
- 对无法自动验证的 UI 体验、真实支付、部署行为等保持“待人工验收”，不得伪造完全通过。
- 最终报告需列出：已完成任务、阻断任务、未覆盖 AC、风险、集成测试与交付入口。

以下是**概念示例，不是已经批准的 JSON Schema 或现有 Bridge 协议**：

```json

  "project_id": "finance-app",
  "repository": "approved-repository-key",
```

## 6. 工程安全与治理：不可弱化的规则

1. **确定性 Bridge 是最终执行决策者**：Agent 输出只能作为提案与证据，不能直接赋权、放宽测试命令、跳过校验或声明最终通过。
2. **执行边界不随计划扩大**：仓库/目录白名单、可信测试命令、凭据隔离、发布开关、Candidate SHA 与 Reviewer 绑定都沿用或加强。
3. **风险操作需单独授权**：数据库迁移、鉴权、支付、线上服务、付费 API、部署、自动合并、生产数据等；已批准的低风险范围才可连续运行。
4. **限制模型与工程成本**：最大任务数、修复轮次、模型调用预算、最长执行时间、待审 PR 上限等以可配置策略限制；超限安全暂停。
5. **任务与项目均保留证据**：任务卡版本、规划版本、Git SHA、测试日志、审查结果、失败原因、人工审批与最终交付可追溯。
6. **失效时宁停勿冒进**：计划无效、依赖冲突、未授权命令、恢复证据缺失、远端状态不明，不能当成成功。
7. **当前 Windows 测试模式不等于 OS 沙箱**：v0.2 不得以“自动规划”作为处理不可信代码或无人值守生产操作的理由。

## 7. 早期验收标准草案（未来细化）

| ID | 初步验收标准 |
|---|---|
| V02-AC01 | 用户只给项目目标和仓库，系统能生成可审查的 Spec、Roadmap 和任务草案；明确不确定性。 |
| V02-AC02 | 任务图依赖完整、无环、任务都有明确 AC、实施范围和检查方法。 |
| V02-AC03 | AI 生成的任务不能扩大 Bridge 已授权的仓库、测试、网络、发布和费用权限。 |
| V02-AC04 | 计划获得授权后，低风险任务可以按依赖自动连续执行，不必逐张人工派卡。 |
| V02-AC05 | 每张任务仍经过 v0.1 的测试、审查、SHA 与证据门禁；错误结论不得解锁下一任务。 |
| V02-AC06 | 中断后安全恢复，不重复写代码、重复提交或重复发 PR；不能恢复的任务进入人工处理。 |
| V02-AC07 | 失败任务的依赖后续任务被阻断，且原因可见；系统不陷入无限修复或无限拆任务。 |
| V02-AC08 | 项目级集成测试与 AC 证据清单能揭示跨任务问题及待人工验收项。 |
| V02-AC09 | 规划版本、审批、预算和真实执行日志可追溯；超限按策略暂停。 |
| V02-AC10 | 最终成果必须保留人工验收及合并/部署边界，不由 AI 自行宣称产品完全交付。 |

以上仅是**讨论阶段的验收候选**；不应直接当作 v0.2 开发任务或最终合同。

## 9. 多项目并发与模型优化：保留讨论，但不抢第一优先级

### 9.1 双 Worker / 多项目并行

讨论过的候选：

```text
一个 Supervisor
  ├─ Worker A → 项目 A
  └─ Worker B → 项目 B
```

原则：不同项目可以并行；同一项目暂时串行；每个任务具有独立 Worktree / Codex 进程 / 测试环境；SQLite、Journal、任务认领、恢复和发布需并发安全。**禁止简单地在同一队列和数据库上启动两个现有 Supervisor。**

另一个可考虑的简化实验是使用两个**资源完全隔离**的 SoloShip 实例，但这不是最终多 Worker 架构的替代结论。

**当前决定**：先实现项目自动规划及串行连续开发，再评估双 Worker 是否进入 v0.2 后段；若明显扩大风险和范围，移至后续版本。

### 9.2 模型成本与能力评测

曾讨论按任务复杂度路由不同模型、额度感知及低成本模型评测。原则是按**真实代码、独立测试、首次通过率、返工次数与成本**评估，而不是看模型品牌。

**当前决定**：保留为后续优化与实验议题；不纳入 v0.1，也不让它干扰 v0.2 的最小编排闭环。

### 9.3 界面与多后端

可视化看板、动态 Worker 池、多 AI 后端的通用抽象等也讨论过，但不是当前优先能力。先验证项目编排是否真能减少人工干预。

## 10. v0.2 建议分阶段验证（尚未批准）

| 里程碑 | 目标 | 判定证据 |
|---|---|---|
| M0：只规划、不执行 | 对真实项目生成 Roadmap、任务图和 AC；只读审核 | 任务依赖可校验，计划范围合理 |
| M1：人工批准后串行执行 | 复用 v0.1 Bridge，逐张任务按依赖自动推进 | 若干连续任务无需重复人工派卡 |
| M2：跨任务恢复与项目验收 | 持久化项目状态，安全恢复，完成集成测试与总报告 | 崩溃/失败可追溯，整体 AC 有证据 |
| M3：可选性能实验 | 评估双 Worker、成本/限流策略是否必要 | 与串行模式比较收益和额外复杂度 |

## 11. v0.2 正式开工前需要讨论/拍板的事项

1. 首个 MVP 的输入范围：只支持**已有 Git 仓库**，还是同时支持从零创建项目？
2. 规划批准模式：每次批准完整 Roadmap，还是按阶段分批批准？计划变更如何申请再审批？
3. Task Graph 如何与现有 P00/P02 任务协议、数据库和 Journal 对接？
4. PR 策略：每任务一个 Draft PR、每阶段一个 PR，还是最终汇总 PR？如何处理依赖分支？
5. 初版任务数量、模型预算、运行时长、修复轮次及待审 PR 数上限。
6. 用户必须确认的高风险操作范围与人工验收标准。
7. 项目级 AC 证据矩阵使用何种协议、如何处理“无法自动验证”。
8. P05-C 完成后，任务重启恢复能力能否支撑项目级自动连续调度？
9. 双 Worker 是否值得纳入 v0.2 后段，还是留给 v0.3？
10. 采用/借鉴外部项目设计时，哪些能直接复用、有哪些许可证和维护成本约束？

## 12. 与 v0.1 的衔接（不作为立即执行任务）

在开始任何 v0.2 编码之前，先按届时仓库的真实状态验收 v0.1。按本次讨论时掌握的信息，v0.1 收尾重点是：

- **SS-V01-005-R1**：补齐 GitHub PR 来源仓库身份校验。
- **P05-C**：未完成任务恢复与 Supervisor 运行可靠性。
- **逐条 AC 证据矩阵**：让每个验收项可以追溯测试与 Reviewer 证据。
- **端到端验收**：真实成功、失败、修复、重启恢复、PR 与人工接管路径。
- **Windows 安全边界说明**：测试模式不等于 OS 级隔离，不能误宣称已支持不可信任务的无人值守执行。

这些是**2026-10-24 的讨论快照**，不是最新仓库执行状态。恢复讨论时应先读取 `PROGRESS.md`、`docs/AI_HANDOFF.md` 和 Git HEAD 并重新核对。

## 13. 下次继续讨论时的开场检查单

1. v0.1 已通过哪些真实端到端验收？剩余阻断是什么？
2. 确认 v0.2 首要验收目标：**整项目自动拆卡并串行交付**。
3. 决定首个试点项目和边界（项目规模、技术栈、已有仓库/新建）。
